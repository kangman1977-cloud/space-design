【一】實體可以直接展開，加厚改看幾何事實
═══════════════════════════════════════════════════════

  原本 part.js 擋著「不是板件就拒絕展開」。那是鈑金思路：
  鐵板折彎時中性層長度不變，所以資料存中性面，而實體沒有中性面。

  但這套工具實際的做法是**切開再接合**（珍珠板、發泡板、木板、壓克力），
  接縫銑 45 度斜接，板厚由斜面吸收，每一片就是切到**外緣尺寸** ——
  而實體的網格本來就是外表面。直接展開它就是正確答案。

  kang 說明用意時講得很清楚：「像摺紙一樣把展開圖組合起來」。
  摺紙沒有板厚。

【證據：擋的只是標籤，不是幾何】

  同一個 60x45x40 的方塊，標成實體與標成板件，展開結果完全一樣：
    片數 1、面積 13800 cm²、展開長 145、展開寬 210

  13800 = 2 x (60x45 + 60x40 + 45x40)，精確。
  擋著的時候使用者只能手動把種類改成板件繞過去，
  而繞過去拿到的就是同一組數字。

【連帶：加厚的判斷從標籤改成幾何】

  「要不要加厚」原本問 `kind === SHEET`。改成問**網格開不開放**。

  `kind` 是使用者在下拉選單裡隨手可改的標籤，封閉與否才是幾何事實 ——
  跟「板件不該做布林聯集」（踩過的坑第 8 條）是同一條原則。

  用標籤判斷實際會出錯：把封閉的方塊標成板件（在那道門還在的時候，
  這是繞過去的唯一辦法），加厚會得到**兩個互不相連的盒子**
  （內外各一個，實測 shell(0.2) 後獨立塊數 = 2），而不是一個空心盒。
  門拆掉之後這條繞道自然消失，判準也一併改對。

  改動處：exportPanel.js（STL 匯出）、scene.js（畫面顯示厚度、
  單面/雙面繪製）。新增 mesh.isClosed()。

  scene.js 的 _shellThickness() 順便重排條件順序：
  板厚 0 與面數過多不必碰網格就答得出來，放前面；
  isClosed() 對封閉網格要掃完所有半邊，放最後。
  這樣常見情況（實體沒填板厚）根本不會走到掃描。

  kang 實測確認：方塊沒有「已依板厚自動加厚」那一行，折板與平板有。

【二】STL：四邊形面的頂點被共用，dropToBed 把它減兩次
═══════════════════════════════════════════════════════

  ⚠ 這是第 3.5 期就存在的舊 bug，不是這一輪弄出來的。
    kang 在 3D 列印面板上看到平板顯示「印不出來」才發現。

【症狀】

  100x60 的平板加厚後放在 Y=44cm 處匯出：
    dropToBed 前   外框 1000 x 600 x 2 mm     體積 +1,200,000   ✓
    dropToBed 後   外框 1000 x 600 x 439 mm   體積 -86,600,000  ✗

  面板判定「法向朝內（體積算出來是負的），印出來會內外相反」。
  但那是**症狀**，不是原因。

【原因】

  triangles() 做扇形三角化時，`p0` 是每個面算一次給所有三角形共用的：

      const p0 = put(vs[0].p);
      for (let i = 2; i < vs.length; i++) {
        const a = p0, ...
        out.push({ a, b: b.clone(), c: c.clone(), ... });   // a 沒有 clone
      }

  一個四邊形切出來的兩個三角形因此**共用同一個 Vector3 物件**。
  dropToBed() 是就地平移（t.a.z -= z），共用的那個頂點被減兩次，
  薄板整個被扯開 —— 2mm 變成 439mm，體積翻負。

  -> 修法：三個頂點都 clone，包含 a。

【為什麼一直沒被發現】

  · 三角形面（方塊、圓錐、球）每個面只產生一個三角形，共用不到。
    這個 bug 只在**有四邊形面**的東西上發作 ——
    平板、折板、管、圓柱側面、圓角方塊，而那正是板件。
  · 物件**在原點時不發作**：dropToBed 的位移是 0，直接 return。
  · 第 3.5 期的外部驗證（另寫 Python 解析器 ＋ kang 用線上工具）
    用的是**錐體** —— 剛好是不受影響的那一類。
  · 折板其實也一直是壞的（外框 1030.8mm 應為 321.8mm），
    只是體積剛好還是正的，沒被判「印不出來」，所以沒人注意。

【測試補在哪】

  原本的測試量的是 mesh.volume() 與加厚後的體積 —— 那兩個一直都對。
  壞掉的是走完 matrix -> zUp -> scale -> dropToBed **全程**之後的結果。

  -> 新測試改成跑完整條匯出路徑再驗，而且刻意把物件放在 (108, 44, 0)。
     六種形狀（平板、折板、管、圓柱、圓角方塊，加方塊當對照）
     各驗體積、外框 X、外框 Z、貼平台 z=0。
  -> 另外直接測**病因**：任兩個三角形不可共用同一個 Vector3 物件。
     症狀會變，病因不會 —— 日後有人為了省一次 clone 又改回去，
     這條會立刻擋下。
  -> 再加一條：dropToBed 跑兩次體積不變。

【教訓】

  **「中途對、最後錯」的 bug，只測中途抓不到。**
  凡是有多段轉換的輸出路徑，驗證要放在**最末端**，
  而且要用「跑完全程之後仍然守恆的量」去對（這裡是體積與外框）。

  另一條：外部驗證挑的樣本要涵蓋不同的**網格結構**，不只是不同的形狀。
  錐體與平板在使用者眼中是兩個形狀，在這個 bug 眼中是
  「全三角形」與「有四邊形」兩類 —— 只驗了前者等於沒驗。
