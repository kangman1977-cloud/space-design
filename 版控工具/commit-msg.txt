鋼筆：放開手的清理永遠沒執行 —— kang 講對了四次，我三次沒抓到

kang 2026-08-29 第四次退回，要我「直接進網頁用鋼筆畫一個圓圈」。
畫出來是一團有尖角的東西 —— 而那一畫就把根本原因逼出來了。
動到 3 個檔（select.js / index.html / main.js）＋ STATUS.md。

────────────────────────────────────────────────
【🔴 根本原因：一行 return 的位置】

  js/view/select.js 的 pointerup：

      // 拖曳過、按太久、或正在操作 gizmo → 不算點選
      if (dist > TAP_MOVE || dt > TAP_TIME) return;    ← 這裡
      ...
      if (this.penMode) { ... this._penDown = null; ... }   ← 走不到

  🔴 鋼筆的「按住拖」必定超過 TAP_MOVE(8px)
     → pointerup 在走到鋼筆那一段之前就 return
     → 【放開手的清理永遠沒有執行】
     → _penDown 一直留著
     → 之後每一次移動游標都還被當成「正在拖」
     → 【上一個錨點的把手被改寫成「指向游標」】，直到按下左鍵才停

  ✅ 修法：把鋼筆那一段【搬到那道 return 之前】。

【🔴 kang 說的每一句都是字面上的事實】

  「不點左鍵..曲線會一直處於開放狀態」  → 曲線【真的】還在變
  「左鍵重疊了曲線與第三點的確認」      → 那一按同時停住曲線又放下一點
  「控制曲線應該要比放點先」（第一次講的）→ 同一個病的另一種說法

  ⚠ 他從第一次就講對了，⛔ 而我三次都沒抓到。

【🔴🔴 我為什麼三次都沒抓到 —— 量錯了量】

  上一輪我去線上版「實測」，量的是【錨點數】：
      按下→拖→放開 ＝ 1→2→2  ← 看起來完全正常
  於是我下了「邏輯是對的，說謊的是畫面」這個結論，跑去改顏色。

  🔴 而病在【把手的數值】，⛔ 不是錨點數。
  【實證】這一輪把 localStorage 裡存下來的資料挖出來：
      錨點 A0 = ( 32.15,  0.00)
      出把手  = (-32.15, 34.98)   ＝ 正好是「A1 − A0」整條弦
      長度 47.5 > 半徑 32，方向也不是切線
  → 把手根本不是我拖出來的那一段，而是「指向下一個錨點」。

  ⭐ 教訓（已升格成鐵律，見 STATUS 那則指標）：
     「先量再改」是對的，⛔ 但量錯量比不量更危險 ——
     它會給你一個看起來有根據的錯誤結論，然後你就去改沒病的地方。
     🔴 判準：【要量的是「使用者說壞掉的那個東西」本身】。
        他說的是「曲線」，我量的卻是「點數」。

【順帶：kang 指定的手勢也做了】

  · 左鍵          ＝ 放點（位置定案）
  · 右鍵按一下     ＝ 確定這一段曲線（線不再跟著游標跑）
  · 右鍵拖        ＝ 轉視角（⛔ 沒有被吃掉，用移動距離分）
  · 平板：多一顆「確定曲線」按鈕 —— ⚠ 平板沒有右鍵，
    跟「吸中點」同一條理由（那顆的註解寫著「不是方便，是平板唯一的路」）

  ⚠ 這一件本來是【bug 的替代方案】，而 bug 已經修掉了 ——
     但 kang 指定要，而且它本身是有意義的控制，所以留著。
