擠出面介面 ＋ 兩個實測 bug ＋ 新方向：功能邏輯不從推論來

測試 1013 -> 1027 項。這一次存檔涵蓋三件事。

一、擠出面的介面（方案 C，kang 拍板）

選面 -> 按「擠出」-> 立刻長出一個吸附格距 -> 新蓋子自動選中
     -> 用已經驗過的「拉面」拉到想要的長度

不用拖曳決定距離，是因為擠出是拆掉重建，拖曳要每幀重建網格。
C 完全不需要新的拖曳邏輯。extrudeFace 多回傳 capFace，
select.js 加 selectFace()（一定要在 commit() 之後叫），
按鈕啟用狀態接到 updateBar()。

二、kang 實測抓到的兩個 bug

1. 選到面之後「擠出」還是灰的，要先拖一下 gizmo 才會亮。
   成因＝pickEdit() 直接掛 gizmo、不走 _refresh()，所以 onChange
   （裡面才有 updateBar）不會被觸發，而 editPick() 也只叫了 panel.refresh()。

2. 反方向拉會跳一串紅字「少 13 條折線多 10 條折線、13 個面已經不平了」。
   查出來只有一種情況會報：把蓋子拉回原位，側牆被壓成零面積 ->
   computeFaceNormal 算不出法向 -> facePlanarity 回傳「不平」。
   那不是「不平」，是「被壓扁了」—— 零面積的面其實是平的（所有點共線）。
   又是坑第 20 條：偵測是對的，講出來的意思是錯的。
   修法＝facePlanarity 多回傳 degenerate，另開 degenerateFaces()。

   而且紅色也用錯了。坑第 28 條：紅色只留給「程式做不到你要求的事」，
   那是使用者自己拉的。改成藍色，並拿掉每拉一下都在變的折線增減。

三、⭐ 新方向：這個專案的功能邏輯不從推論來（kang 定調）

起因是 kang 指出建模器很多功能邏輯是推論出來的，而 Blender 有完整的
官方文件與開源程式碼，功能邏輯可以直接參考。當天的證據很清楚：
「把一個頂點旋轉 30 度沒有意義」這句推論，讓我一行把 gizmo 鎖成只能平移，
梯形、收尖、擠出後轉方向全被鎖死；而「變換 ＝ 種類 x 方向 x 中心」
這三個正交概念是查了才知道的。

新增 外部參考調查.md，內容：
- 兩條界線：Blender 與其擴充都是 GPL -> 讀邏輯不抄程式碼；
  Pepakura 是商業軟體 -> 只讀公開文件與行為
- 過篩子的判準：「這個對板材切割/展開/剖面分切有沒有用？」
- 研究線一（編輯 -> Blender）與線二（展開 -> Pepakura ＋ 兩個開源展開器）
- 已經查到的部分，免得下次重查

⭐ 展開那條查到一個直接打到痛點的：Blender 內建的 io_export_paper_model
用 Seams 定義切割線＝我們的指定分片，而且它「必要時會自動補刀」——
那正是我們「重疊只偵測不自動解」的缺口。而它是 GPL、原始碼讀得到。
