## 回歸測試（改動核心模組後一定要跑）

```
node 建模器/tests/run.mjs
```

**1231 項全部是用數學對答案的**，不是「看起來沒錯」。對不上就是改壞了。
第一次跑會自動建立 `建模器/node_modules/three` 墊片，讓 Node 也能解析
`import 'three'`（瀏覽器是靠 importmap）。

沙箱下載不到瀏覽器，所以「畫面有沒有出來」永遠只能靠 kang 實際開啟確認。
但**能用數學驗的部分就一定要驗** —— 建模器的核心刻意跟 three.js 場景與 DOM
切開，就是為了這件事。第 3 期的出圖也照這條做：`drawProgram()` 只產生
一串純資料的繪圖指令，Canvas 與 SVG 兩個算繪端各自照著畫，
**所以「圖上標了什麼、有沒有疊在一起」在 Node 裡測得到**。

| **母物件轉過 90 度之後拆開** | 位置照樣對得上。只把本地偏移量加上去的話，一轉過角度就會散開 |
| 拆得開／拆不開 | 多形狀的匯入件可以；單形狀、方塊都不行 |

第 6 期地基（變換 ＝ 種類 × 方向 × 中心）的基準：

| 項目 | 結果 |
|---|---|
| 方向基底的 Z | **就是面法向**（方塊頂面 → 世界 +Y） |
| 三軸 | 互相垂直、都是單位長、**右手系**（X×Y ＝ Z） |
| 面的切線 | **最長的那一條邊界邊**（頂面 60×40 → 沿世界 X） |
| 結果唯一 | 同一個面問兩次，兩個四元數的夾角是 0 |
| 退化 | 認不得的 kind／`face:null`／`el:null` 一律 `ok:false`，**不丟例外** |
| ★ **沿法向拉 Z 10 ＝ `pushFace(10)`** | 體積都是 132000，而且**每一個頂點都在同一個位置**（兩條路對答案）|
| ★ 頂面兩個切線各縮一半 | 棱台體積 **63000**（擬柱體公式 45/6×(2400+4×1350+600) 手算）|
| ★ 取消（`restoreVerts`） | 體積精確回到 108000，**每一個座標跟拖之前一模一樣** |
| ★ 繞法向轉 37 度 | 剛體運動（頂點間距離不變）、**面仍然在原平面上** |
| ⚠ 繞法向轉 180 度 | 位置**集合**回到原樣，但**體積 108000 → 36000**（側牆被扭成麻花）|
| 斜面（圓柱側面）沿法向推 | 體積**變大**（繞向錯了會變小，坑第 29 條）|
| 快照長度對不上 | **一個頂點都不動**，體積沒被碰到 |

多選（1-3）的基準：

| 項目 | 結果 |
|---|---|
| ★ **聯集去重** | 頂面 ＋ 右側面 ＝ **6 個頂點不是 8 個**（共用 2 個）。不去重那 2 個會被平移兩次，而畫面上看起來只是「拉太多了」 |
| ★ 一起移動 | 移動 6 個頂點，**每一個都剛好走 10**（共用的沒有走 20） |
| 同一個元素放兩次 | 還是 4 個頂點（函式本身要撐得住） |
| ★ **兩種中心真的不一樣** | `active` ＝ 右側面重心 (30, 0, 0)；`median` 與它相距 > 1cm |
| ★ 順序即 active | 把兩個對調，`active` 中心從 (30,0,0) 換成 (0, 22.5, 0) |
| 單選時 | 兩種中心是**同一個點**（介面上那句「看不出差別」不是隨口說的） |
| ★ **多選法向取和** | +Y 與 +X 兩個面 → Z ＝ (0.7071, 0.7071, 0)，**剛好指在兩面中間** |
| 合併後仍正交右手系 | X·Y ＝ Y·Z ＝ 0、X×Y·Z ＝ 1（合併最容易壞的地方） |
| ★ **權重相同** | 同一個面放兩次，Z 方向完全不變（不會被三角形多的區域壓過） |
| ★ **切線照 active** | 對調兩個面的順序：Z 完全一樣，但**整組基底會轉**（切線換人了） |
| 空陣列 | 頂點 0 個、基底 `ok:false`（退回世界） |

拆掉重建的三個配件 ＋ 面合併的基準：

| 項目 | 結果 |
|---|---|
| 🔴 **預檢抓得到四種壞資料** | 合併頂點的天真寫法 → **2 個退化面 ＋ 1 個孤點**；指到不存在的頂點 → **fatal**（修不掉，要擋）；重複的面 |
| ★ **清乾淨之後 χ 回到 2** | 清 2 個退化面 ＋ 1 個孤點 → V7 F10 χ2 封閉；體積 **72000**（那個角被抹掉了，手算得出來）|
| 🔴 **remap 證明索引真的會位移** | 原頂點 **7 → 6**；頂點 0 沒動；被清掉的 1 沒有對應。**這就是「既有頂點保持原索引」那個契約破掉的證據** |
| ★ **面合併不改變幾何** | 方塊 12→6、圓柱 128→34、球 960→512，**體積與面積全部相對誤差 1e−7 內**（實際小數點後 6 位全同）|
| ★ **合併後 χ 仍是 2** | 孤點有清掉。不清的話圓柱會變 χ4，而 `validate()` 照樣回 `ok=true` |
| ★ **四邊形面數** | 方塊 6／圓柱 32／球 448 —— **那是環切的 ring walker 要走的東西** |
| ⚠ **管：一個面都不合併** | 側面本來就是四邊形；兩個端面是**環形**（兩個迴圈），一個面裝不下。而且**理由要講出「環形」**，不是一句「沒得合併」帶過 |
| ★ **合併之後 CUT 一條都沒少** | 索引位移了也要搬 —— 走 remap 自己配一次，不能靠 `_copyMarksTo()` |
| ★ **選取搬得過去** | 點／邊／面三種都驗；面是用**共面區域的頂點索引集合**配對，搬到的是合併後那個四邊形 |
| 被清掉的孤點 | 搬不過去就**安靜地掉掉，不丟例外** |

壓平 ＋ 溶解面的基準：

| 項目 | 結果 |
|---|---|
| ★ 壓平 3 片相鄰側面 | 移動 8 個頂點，回報壓平前偏離 **0.478 cm**（使用者要付的代價） |
| ★ 壓平後 | 8 個點**全部落在同一個平面上**（1e-9 內） |
| ★ 那三片變成同一個共面區域 | 34 → **32** 區 |
| ★★ **併成一個面是免費的** | 再跑還原多邊形 → F 34 → 32，那三片變成一個 **8 邊形**，不平度 < 1 微米 |
| ★★ **選取搬過去要去重** | 三個舊面全指向同一個新面 → 必須回 **1** 筆。不去重「選了幾個」會說 3 而畫面只有一個 |
| ★ 展開總面積變了 | 形狀真的被削平了，這是預期的 |
| ★★ **對照：直接溶解不壓平** | 那個 8 邊形偏離平面 **0.956 cm ＝ 可切容許值的 96 倍** —— 這一條釘住「為什麼溶解面不做」 |
| ★ 本來就平的面 | `before = 0`，體積一格都沒動（呼叫端據此講「本來就是平的」，不記 Undo） |
| 只選一個點 | 擋下來並說「至少要選到 3 個頂點」 |

沙箱驗不了「別人的軟體讀不讀得動」（鐵律五）：

| 項目 | 結果 |
|---|---|
| 水密（封閉表面） | **是** |
| 判定 | **可直接列印 —— 防水且多歧管（manifold）** |

⭐ **那個 124/64 自己就是一份交叉驗證**：
32 個側面四邊形 ×2 ＝ 64，加兩個 32 邊形端蓋各 30 個 ＝ 60，合計 **124**；
頂點上下各 32 ＝ **64**。
若端蓋還是原本的扇形，會是 **128 個三角形 / 66 個頂點**（多出兩個扇心）——
**所以還原多邊形與耳切兩件事都在正確運作**，而且是從外部工具的數字反推出來的。

⚠ 兩個案例都測了（往外拉 63.5cm 寬、往內拉 48.1cm 寬），都是水密。

🔴 **「轉 180 度」那一條原本斷言「體積必須不變」，實測是 36000。**
推論的時候把「四個角的位置集合不變」讀成「每個點回到自己的位置」。
**這種事不能靠推理，要靠對答案**（鐵律二）。

（上下緣 64 個頂點是折角、有角虧），可展的是側面。展開時本來就會把
上下蓋當成另外的片。這一點寫測試時搞錯過一次。
